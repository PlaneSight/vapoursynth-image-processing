# Development guide

The repository has one cross-platform developer interface: `uv run vsip`.
uv owns the Python 3.14 environment and documentation dependencies; the CLI in
turn coordinates the Rust workspace, Zensical, and optional VapourSynth smoke
tests. Direct Cargo commands remain available for focused investigation, but
the CLI defines the checked project workflows.

## Bootstrap a checkout

Install [uv](https://docs.astral.sh/uv/) and rustup, then run these commands from
the repository root:

```text
uv python install 3.14
uv sync --locked
uv run vsip info
```

`uv python install` obtains a managed Python build when Python 3.14 is not
already available. `uv sync --locked` creates or updates the local `.venv` from
`uv.lock` and fails if the project metadata and lock disagree. There is no
manual virtual-environment activation step and no supported `pip install`
workflow.

The committed Python requirement constrains the project to Python 3.14. uv uses
the repository's Python-version preference when selecting an interpreter, so
subsequent commands stay on that series.

## Keep Python dependencies reproducible

`pyproject.toml` is the authored packaging and tool configuration. `uv.lock` is
the reviewed, cross-platform resolution and must be committed whenever a
dependency change alters it.

Use uv to change the environment:

```text
uv add <runtime-package>
uv add --dev <development-package>
uv remove <package>
uv lock --check
```

Do not edit `uv.lock` by hand. Use `uv sync --locked` and `uv run --locked ...`
in reproducible jobs; omit `--locked` only while deliberately updating project
requirements and regenerating the lock.

The installed Python package provides the `vsip` console entry point. Always
invoke it as `uv run vsip` from a checkout so uv selects the project environment
and verifies that the command's Python dependencies are present.

## Understand the Rust toolchain split

The repository deliberately carries three Rust compatibility levels:

| Rust version | Scope | Reason |
| --- | --- | --- |
| 1.85 | Pure shared crates, scalar kernels, plugin-family APIs, and `xtask` | Public minimum supported Rust version for the runtime-independent graph. |
| 1.88 | Complete VapourSynth adapter graph | The pinned `vapoursynth-rs` dependency reaches `libloading` 0.9, whose MSRV is 1.88. |
| 1.97.1 | Normal development, full checks, and releases | Pinned by `rust-toolchain.toml`, including rustfmt and Clippy. |

Install the compatibility toolchains once if `uv run vsip info` reports them
missing:

```text
rustup toolchain install 1.85.0 --profile minimal
rustup toolchain install 1.88.0 --profile minimal
rustup toolchain install 1.97.1 --profile minimal --component clippy --component rustfmt
```

The default toolchain file selects 1.97.1 automatically inside the checkout.
The CLI uses explicit `+1.85.0` and `+1.88.0` Cargo invocations only for the
corresponding MSRV gates; it never weakens the declared compatibility of pure
crates to accommodate runtime adapters.

## Use the development loop

For a small edit, start with focused and quick feedback:

```text
uv run vsip fmt
uv run vsip check --quick
uv run vsip test --profile debug
```

Before handing off a change, run the full local gate:

```text
uv run --locked vsip ci
```

For a targeted native build, pass Cargo package names explicitly:

```text
uv run vsip build --release --package vs-masklab-vapoursynth
```

Use `uv run vsip package` when validating the Python source distribution and
wheel. Packaging the CLI does not package the platform-native adapter
libraries; those remain explicit Cargo release artifacts.

See the [CLI reference](cli.md) for the complete command surface and the exact
smoke-test path options.

## Preserve the runtime boundary

The pure algorithm graph must not import VapourSynth bindings. A plugin-family
crate exposes typed configuration, validation, scalar algorithms, and a filter
catalogue. Its corresponding `adapters/*-vapoursynth` crate translates
VapourSynth calls into that API through `vsip-vapoursynth`.

The shared adapter layer owns the recurring boundary work:

- validate formats, dimensions, frame rates, and temporal dependencies;
- copy padded frame rows into exclusive, tightly packed scratch leases;
- convert supported u8, u16, and f32 planes under one numeric policy;
- invoke pure APIs with caller-owned outputs;
- copy results into VapourSynth-owned destination frames; and
- translate typed failures and panics into host-visible errors.

Adapter source contains no handwritten unsafe blocks. The only admitted unsafe
ABI code is generated by the export macro from the pinned
`rust-av/vapoursynth-rs` revision. Do not retain a frame borrow beyond its
callback, duplicate frame-conversion logic in a plugin adapter, or hold a
scratch-pool lock while a kernel executes.

Keep scalar implementations authoritative. Parse configuration, allocate or
acquire scratch, and choose dispatch outside pixel loops. Performance claims
require representative release benchmarks, generated-code inspection, and
differential tests over odd extents, padded strides, and dispatch tails.

## Write and preview documentation

Zensical consumes the authored Markdown pages and the repository's Zensical
configuration. Preview edits with:

```text
uv run vsip docs serve
```

Before committing, build the production site:

```text
uv run vsip docs build
```

Internal links should be relative, headings should be stable and descriptive,
and commands should use `uv run vsip` rather than platform-specific wrapper
scripts. Never edit or commit the generated `site/` tree.

## Validate native adapters

Rust CI does not need a system VapourSynth installation. Runtime smoke tests do
require an R4-compatible `vspipe`, so run them on an artifact-producing host:

```text
uv run vsip smoke all
```

Smoke commands build the release workspace by default and use
`target/release`. Pass `--no-build` only when validating artifacts that already
exist. The CLI converts supplied `--plugin-dir` and `--masklab-plugin` values to
absolute paths and configures the `.vpy` process. Do not replace these
arguments with instructions to set environment variables manually; path
arguments are the portable interface.

## Manage generated artifacts

Generated files have explicit ownership and retention rules:

| Path | Producer | Tracked | Policy |
| --- | --- | --- | --- |
| `uv.lock` | uv resolver | Yes | Commit reviewed resolution changes. |
| `.venv/` | `uv sync` / `uv run` | No | Disposable local Python environment. |
| `target/` | Cargo | No | Build cache and native outputs; never archive wholesale. |
| `site/` | Zensical | No | Rebuild and deploy; never edit or commit. |
| `dist/` | Release tooling | No | Publish only selected, verified deliverables. |
| `.tmp/` | Tests and tools | No | Must be disposable. |
| `.cache/` | Explicit local tools | No | Must never be required for correctness. |

Authored sources are never cleanup targets. Build scripts may write only below
Cargo's `OUT_DIR` and may not access the network. Before introducing another
artifact class, define its producer, cleanup behavior, tracking decision, and
CI treatment in the [artifact policy](artifacts.md).
